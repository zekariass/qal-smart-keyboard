# ADR 0007: UX and open-item decisions (alpha)

- **Status:** Accepted for the M1/M2 alpha. Items marked **PROVISIONAL (G0)** stand until the native-speaker panel (gate G0) reviews them.
- **Date:** 2026-11-17
- **Context:** Implementation steps C1.3, A1.3, A1.4 and B1.3–B1.6 raised questions for the product owner and the language panel. The product owner delegated these decisions to engineering, which took the recommended option for each. Each decision below is recorded so agents implement it consistently and the panel can overturn it.

## Keyboard UX (product)

| # | Question (source) | Decision | Why |
|---|---|---|---|
| U1 | Should a language switch (globe tap) land in the target language's native layout or stay in ABC? (A1.4) | **Land in the target language's last-used native layout**, as built. ABC is a per-language toggle, not a global state. | The globe means "change language". Staying in ABC would make every switch to an Ethiopic language look like nothing happened. |
| U2 | Should long-press on space open a picker or cycle languages? (A1.4) | **Picker** (slide and release), as built. | This matches the common Android convention. With four languages, cycling is slower and gives no overview. The globe tap already cycles. |
| U3 | Should a fresh install start on the am Fidel grid or ABC? (A1.4) | **Phonetic QWERTY for am/ti.** The first active language is am until onboarding (A1.7) sets the user's choice. ABC is used only while the core or packs are loading. | Most smartphone users in Ethiopia and the diaspora already type on a Latin QWERTY layout (SD J2). Fidel is one globe long-press away. SD §26 still lists the onboarding default as a panel item, so this is **PROVISIONAL (G0)**. |
| U4 | Should autocorrect run on Space in phonetic mode? (A1.3) | **No, suggestions only** for the alpha. The C1.7 harm-guarded autocorrect stays unwired until evaluation sets exist for the language (gate G1). | Auto-replacing Ethiopic words without evaluated data risks corrupting text, which is the harm the guard exists to prevent. |
| U5 | Which label marks unreviewed language data on the strip? (A1.3) | **Keep "DRAFT"** for internal and alpha builds. It disappears automatically when the profile status becomes APPROVED. | The label is aimed at testers, and rule N9 requires it. Public builds cannot ship DRAFT profiles anyway. |
| U6 | Homophone alternatives push dictionary words off the strip, and frequency does not reorder homophones. (A1.3, SD 7.2) | Index 0 stays the literal rule output, so Space commits exactly what was typed. **Homophone alternatives are sorted by dictionary frequency**, so the conventional spelling comes first after index 0. **At least two strip slots are reserved for dictionary completions** when the lexicon has any. | This follows SD 7.2 ("dictionary frequency picks the conventional spelling") without silently changing the user's input. Implemented as a core follow-up after A1.6 (it touches `engine.rs`). |
| U7 | Should the A1.9 device matrix include fields that reject composing text? (A1.3) | **Yes.** Add a `TYPE_NULL` terminal app and a Chrome/WebView text field. | These fields exercise the direct-commit fallback from ADR 0004, which so far has only been tested in unit tests. |

## Language layouts: PROVISIONAL (G0)

| # | Question (source) | Decision |
|---|---|---|
| L1 | What should a tap on `.` and `,` produce in the Fidel grid? (A1.4) | **Fidel grid only:** a tap gives ። and ፣. ASCII `.` and `,` come first in the long-press popup. Phonetic, Qubee, English and ABC keep ASCII on tap. |
| L2 | Should Amharic keep the ኸ series? (C1.3) | **Keep it.** It appears in common Amharic charts and loanword spellings, and it costs one key. |
| L3 | Should the homophone series ሐ ሠ ኀ ዐ ፀ be on the main grid or behind long-press? (C1.3, A1.4 density) | **Keep them on the main grid for now.** The panel decides in G0. If the grid proves too dense on 5-inch phones in A1.9, they move behind long-press of ሀ/ሰ/ሀ/አ/ጸ. That change is to layout data only (new pack version), not code. |
| L4 | Which order should a consonant tap show first in two-key entry? (C1.3) | **Sixth order** (the consonant without a vowel), as built per SD §7.2. This is one field per layout (`defaultOrder`). |
| L5 | What should the mode labels say? (A1.4) | Keep `አማ`/`ትግ`/`OM`/`EN` plus `ፊደል`, `QWERTY`, `Qubee`, `ABC→አ`. |

## Backend and data

| # | Item | Decision |
|---|---|---|
| D1 | OI-P6: shredding and backups | Deletion completes when the last backup containing the wrapped DEK expires. **Backup retention is capped at 30 days.** The privacy notice says "deleted within 30 days from backups". KEK versions are rotated, and versions older than the retention window are destroyed. This must be implemented with the cloud KMS (OI-04) before launch (gate R-privacy, Phase 3). |
| D2 | OI-P7: dictionary `word_hmac` key | A **separate per-user HMAC key** (wrapped like the DEK, never rotated with it, destroyed by crypto-shred) is added in a V-migration when B3.6 needs it. |
| D3 | OI-P8: who owns `user_data_keys` | **`platform.crypto` owns the table.** SD §20.2's Identity listing is updated when the SD is next revised. Columns for wrap algorithm and KEK version are added only when a second KMS provider exists. Callers must store `EncryptedValue.keyVersion()`. |
| D4 | OI-P9: migrations after V1 | `docs/Ethiopian_AI_Keyboard_Database_Design_v2_0.sql` stays the **V1 baseline only**, byte-identical to `V1__baseline.sql`. Changing it would change the Flyway checksum. **V2 and later are canonical in `backend/src/main/resources/db/migration/`**, and each one is listed in the plan's Notes log entry for the step that adds it. |
| D5 | OI-P10: 426 is missing from the contract | A shared `components.responses.AppVersionUnsupported` (426 Problem) was added, and the Conventions text references it. Operations do not list it one by one, because it applies to every `/api/v1` operation except those exempt under B1.6. |
| D6 | B1.3: the 5xx handler logs the full throwable | **Kept for now.** The logging redaction filter that SD §19 requires, verified by tests, is a Phase 3 hardening item and will also cover exception messages. |
| D7 | Rust toolchain on the dev machine | **Accepted.** A1.1 installed Rust and cargo-ndk on the host for Android builds. Core checks keep using the pinned Docker toolchain (`rust:1.91`), matching CI. |
| D8 | Refresh-token reuse versus lost responses on poor networks (B2.4) | SD 9.3 revokes the whole family on any reuse, including a client retry after a lost response, which is common on slow or intermittent Ethiopian mobile networks (OI-R4). **Add a grace window (default 30 s):** if the presented ROTATED token's direct successor has never been used and the reuse is within the window, rotate again from the presented token (revoke the unused successor, issue a new one) instead of revoking the family. Any other reuse revokes the family as before. Clients still serialise refresh calls (A2.x). SD 9.3 gets this amendment. Implemented as the B2.4 follow-up. |
| D9 | Contract gaps found in B2.1/B2.4 | (1) Add optional `installationId` to `OtpStartRequest`, so the per-device limit also applies to start. (2) Declare 403 `ACCOUNT_SUSPENDED` on `otp/verify` and `auth/refresh`. (3) An invalid bearer on an optional-auth operation **stays a 401** (fail loudly, never silently downgrade to anonymous); declare 401 on those operations. (4) Declare 400 on `auth/refresh`. (5) The contract's `UserProfile.marketSource` enum is aligned to the SQL CHECK list (SQL is canonical for stored values). Done in the B2.4 follow-up. |
| D10 | Source of production pack trust keys for release builds (A1.6) | **Production public keys are committed** in a repo key file (public keys are not secrets), and release CI passes it via `-Pqal.packTrustKeysFile`. Private signing keys never enter the repo; they live in the KMS used by the backend pack-signing pipeline (B3.x). Bundled seed packs must be re-signed with the production key before any release build (the DEV-key refusal already enforces this). |
| D11 | Missing or corrupt `versions.txt` (A1.6) | **Keep failing open** (log it, no version floor for that run). Anything able to delete that app-private file can also write packs into the same app-private directory, so failing closed adds no protection and could leave the keyboard without packs. |
| D12 | Should the onboarding step survive process death? (A1.7) | **Yes:** keep the current step and the language draft in the ViewModel's `SavedStateHandle`, so returning from system settings after Android killed the app resumes the same step. Small follow-up. |
| D13 | Agents and physical devices | Every `adb` command an agent runs must name the emulator explicitly (`-s emulator-NNNN`). Agents never install to or clear data on a physical device. |
| D14 | Should `/auth/guest` resume an existing guest? (B2.3) | **No, create only** until the attestation verdict is bound to the installation (App Attest key id, Play Integrity request hash). The installation id is client-sent, so resuming on it would allow guest takeover. A reinstalled app gets a new guest; B2.6 linking preserves data for users who sign in. |
| D15 | Devices list has no HTTP operation (B2.5) | **Add `GET /devices`** (caller's devices, no push token) to the contract docs, sync, and expose `DeviceService.list`. Small follow-up. |
| D16 | Consumers for `devices.device.revoked` and `identity.refresh_token.reuse_detected` | Implemented with the notifications work (push/SMS/email templates), not before. |
| D17 | The OAuth `nonce` is client-chosen, so a stolen, still-valid Google ID token (about 1 h) can be replayed (B2.2) | **Add a server-issued, single-use OAuth nonce** (reuse the B2.3 nonce store: issue, bind to installation/platform, consume atomically) and require it on `/auth/oauth/{provider}`. Contract change, scheduled before public launch (M3 hardening). Accepted for the alpha because the token must first be stolen from the device. |
| D18 | Should a typed word be learned on first sighting? (A1.8) | **No: auto-learn on the second sighting** (kept as a pending count in the encrypted store), so one-off typos are not learned. Explicit add from the strip and settings stays immediate. Small follow-up. |
| D19 | Should BETA packs require a token? (B3.1) | **No.** BETA packs are signed, verified on device and rollout-limited, so discovery stays open. INTERNAL stays gated (token + server switch) until a tester role exists. |
| D20 | Contract gaps found in B3.1 and B2.6 | Fix in one contract-cleanup follow-up (docs copy, then sync): profiles summary says ACTIVE but returns ACTIVE+RETIRED; add `GLOSSARY` to `ResourceType`; align `deviceRequirements` names with the V1 column comment (contract names win, comment updated); `Language.inputModes` source; declare 429/400 where returned; document rollout bucketing; define `mergedGuestUserId`/`isNewUser` for upgrade-in-place and the at-most-once merge; a distinct code for an expired guest bearer on sign-in. |
| D21 | Transliteration profile codes differ between Android (`AM_PHONETIC`, derived from the core profile id) and the backend (`AM_PHONETIC_QWERTY_TO_ETHIOPIC`) (B3.3) | **The backend `profile_code` is the single canonical code.** The B3.2 publisher writes it into each rules pack's profile id; `language-data` profiles are renamed to the canonical codes at the next pack build; Android takes codes from `GET /languages/{code}/transliteration-profiles` (or the pack) and stops deriving them. Android sync never sends PHONETIC mode without a profile code (fall back to DIRECT_SCRIPT_LAYOUT or defer the sync). Done in A2.x. |
| D22 | Entitlement edge cases (B4.1) | DELETION_PENDING accounts keep typing (ungated) but lose AI features (as built). **Add a 24 h renewal lag:** an ACTIVE subscription just past `current_period_end` keeps access for `qal.entitlements.renewal-lag` (default 24 h) so late store notifications don't cut off paying users. Cache invalidation subscribes to billing/organisation outbox events when those modules exist (M4); until then the 30 s TTL plus `invalidate(userId)` apply. |
| D23 | Consent edge cases (B3.5) | Repeated identical decisions are **still appended** (re-acceptance is useful evidence). A **minimum document version** for `TERMS_ACCEPTANCE` and `PRIVACY_NOTICE` becomes configurable; callers below it get `CONSENT_REQUIRED` and the client re-asks. Scheduled with the full privacy notice text (M3). Consent history and document-version endpoints join the D20 contract batch. |
| D24 | The per-account app-rule HMAC key has no delivery operation, so app rules can't work end to end (B3.4) | **Add `GET /me/app-destination-rules/key`** (bearer, registered or guest, `Cache-Control: no-store`, never logged) returning the base64 key and a key id, in the D20 contract batch; also fix `DestinationProfile` `allOf` (`additionalProperties: true` on the members) and add `NATURAL` to `Tone` or document its omission. Profile cap stays 100; `glossaryId` may later include organisation glossaries the caller can read (with B-org work). Data-key rotation must re-encrypt `user_app_rule_keys`, never regenerate it. |
| D25 | Metering edge cases (B4.2) | A user **time-zone change applies from the next window** (the current window keeps the zone it was created with), so changing zones never grants an extra allowance; same for a plan's reset-period change. A retry with the same `Idempotency-Key` after a failed/released request replays that outcome — clients use a new key for a new attempt (contract wording in the D20 batch). Over-settle is never charged beyond allowance + credits (uncovered units recorded, logged, counted). Realtime sessions (D6.7) get reservation extension. Credit refunds in B4.3 use ADJUSTMENT/REFUND rows (REVERSAL is negative-only). |
| D26 | Credit pack validity and expiry cadence (B4.3) | Purchased packs default to **365 days** validity (SD 15), passed by billing as `expiresAt`; promotions set their own. The expiry job stays hourly (expiry is enforced by the clock regardless; the job only writes EXPIRY rows). Organisation credit accounts come with organisations (Phase 7). |
| D27 | Entitlement token edge cases (B4.4) | **Cap `exp` at the winning source's validity end** (`effectiveUntil` + renewal lag) when that is sooner than iat + 24 h, so a lapsed subscription keeps offline gates for at most the lag + 72 h grace. **Rate-limit** `GET /me/entitlements/token` (60/h per user). No revocation list (only on-device features are affected; server features are re-checked per call). Premium on-device packs get their own catalogue feature code with the pack purchase work. Endorsed key announcements (like pack keys) may later remove the app-release-per-rotation cost. Small follow-up. |
| D28 | Android client follow-ups (A2.1) | A2.2 enables **core library desugaring** in `:app` so API timestamps become typed `java.time` values (minSdk 24). The local-stack test reads the OTP from the WireMock SMS stub's request journal (or a dev-only SMS capture adapter) instead of `-PlocalStackOtpCode`. No API certificate pinning (SD §18, ADR 0016); the pin hook stays off unless a later security review reverses it. |
| D29 | AI provider routing edge cases (B5.1) | DEGRADED providers are routable in B5.2 **only as a last resort**: after every ACTIVE candidate has failed or been skipped (kill switch, cost cap, open breaker), with the same data-policy filter (as built in B5.2). A `Cancelled` provider call is a client abort: release the reservation, no response body. Mock capabilities stay BETA (adapters are refused in prod-like profiles). Real vendors wait for gate G0; each vendor then gets its own migration, adapter and recorded fixtures. |
| D30 | Account deletion edge cases (B6.2) | **Accepted:** the security chain now reads the account row for every access token (registered too), so deleted/closed accounts lose access immediately instead of after up to 15 min; ADR 0006's "stateless" note is superseded. **Refuse** merging a guest into a `DELETION_PENDING` account (the guest stays separate) — small follow-up. When notifications (D16) and export (B6.1) exist, send a reminder 48 h before purge and offer an export link. Billing/store participants come with M4. |
| D31 | Dictionary sync tombstones (B3.6) | Last-writer-wins per word is accepted for a personal dictionary (a re-add after another device's delete revives the word). Tombstones are kept **180 days** (B6.3 retention); a client whose sync cursor is older than the oldest retained tombstone gets a resync-required response (contract change with B6.3) and does a full download. |
| D32 | Android sign-in follow-ups (A2.2) | The `direct` flavour offers **no guest sessions** (Play Integrity needs the Play Store); sideloaded users sign in with phone or Google. The server adds an `attemptsRemaining` extension to `OTP_INVALID` (small backend + contract follow-up) so the client stops counting locally. Age-confirmation wording, the release API host, the Google web client id as an accepted audience and the Play Integrity project link go on the M3 release checklist. |
| D33 | AI pipeline edge cases (B5.3) | `DETECT_LANGUAGE` stays available to `DELETION_PENDING` accounts (typing-adjacent, consistent with B4.1 ungated features) but is refused for SUSPENDED (abuse); declare the 403 in the contract. The `ON_DEVICE_ONLY` preference is **also enforced server-side** with a dedicated 403 code (next contract batch). Replaying a cancelled original answers `PROVIDER_UNAVAILABLE` (documented in the contract). First prompt templates are seeded and approved after the G0 evaluation. A server-side am/ti language-ID model is a later quality item. Until B5.4, a replay of a settled request recomputes uncharged (provider cost, not user charge). |
| D34 | Pack update follow-ups (A2.3) | A key newly marked REVOKED also **quarantines installed (downloaded) packs it signed**, falling back to bundled packs (small follow-up). The release-channel picker is shown only in debug/tester builds for now. The pack mobile-data switch and channel stay device-local (not synced). |
| D35 | AI replay cache storage (B5.4) | **Accepted:** the ≤ 10-minute replay cache lives in an UNLOGGED PostgreSQL table (never in WAL archives, backups or replicas), sealed under the **user's data key** (crypto-shred covers it) instead of Redis with a rotating server key; Redis/Valkey only when load requires it. SD §8/§11.6 amended accordingly ("never in plaintext"). A settled key without a stored fingerprint (older than 24 h) answers `IDEMPOTENCY_KEY_REUSED` rather than a free recompute. Contract batch: `IdempotencyKey` notes that keys older than 24 h may be refused and that a replay keeps the original `requestId` and `usage`; production backups use `pg_dump --no-unlogged-table-data` if logical dumps are taken. |
| D36 | Admin publishing follow-ups (B3.2) | Admin operations stay in the same contract file tagged `x-internal` but are **excluded from public client generation** (Android `:api`, TypeScript types) — follow-up. STABLE publishing will also require datasets with review status APPROVED once dataset review exists. Retired draft uploads get a 30-day bucket lifecycle rule. Devices verify signing-key endorsements per pack spec §7.4 (Android follow-up). Seed rules packs are renamed to canonical backend profile codes (D21) at the next pack build, and the language-ID pack gets a shared pseudo-language code (`mul`) in the catalogue (language-data follow-up). Admin access uses consumer tokens behind `qal.admin.enabled` until workforce OIDC + MFA exists (H-steps). |
| D37 | Android sync follow-ups (A2.4) | Dictionary resync uses a dedicated **410 `SYNC_CURSOR_EXPIRED`** (defined in B6.3); the client's "any 400 on a cursor = resync" fallback is narrowed to that code once B6.3 merges. Periodic background sync uses the same mobile-data switch as pack updates (relabelled "Background updates over mobile data"). Destination-profile/app-rule UI comes with the IME destination chip (A2.5). |
| D38 | AI endpoint follow-ups (B5.5) | A client that disconnects is not detected by a plain servlet thread: the request completes and is charged once, and a retry with the same key gets the cached result — accepted for M2. An async wrapper that cancels the worker on disconnect is a Phase 3 hardening item. Per-endpoint AI rate limits move from constants to configuration (Phase 3). MockMvc over the full context stays the IT convention. |
| D39 | Retention decisions (B6.3) | The periods ADR 0020 marks UNDEFINED are **accepted as defaults** (OTP 24 h, nonces 1 h, reset tokens 24 h, sessions 30 d after the family expires, export rows 30 d after link expiry, outbox published 7 d / dead 30 d, processed events 35 d, closed reservations 13 months, voice/realtime metadata 13 months) and are added to SD §19.2. `ai_requests` gets a daily aggregate table before the 13-month purge (analytics follow-up). Deleted-account tombstones that still have financial rows are cut when the 10-year legal period ends (with the M4 financial purge). Export archive objects get a 7-day bucket lifecycle; log and audio retention are infrastructure settings (release checklist). |
| D40 | AI toolbar follow-ups (A2.5) | **Drop BouncyCastle** (~8 MB): verify the entitlement token's Ed25519 signature through a small `keyboard-core` FFI function (the core already ships Ed25519 for packs), keeping the Kotlin-side JWS/claim checks. **No network on keyboard show:** plan-state/token refresh happens when the user opens the toolbar and from the app's background worker, never merely because the keyboard appeared. Toolbar link buttons deep-link into the companion app's sign-in/settings/plans screens; the last-used destination is remembered per app (device-local). |
| D41 | Feedback and history follow-ups (B5.6/B5.7) | Withdrawing `FEEDBACK_TEXT` **deletes stored feedback comments and content** (the rating stays). `ai_feedback` gets a 13-month retention rule (like `ai_requests`). The app warns when the user enables history on a plan without `HISTORY_SYNC` (A2.6). History needs `saveToHistory: true` in the request (contract default false), the preference, the consent and the entitlement. Small backend follow-up. |
| D42 | Data export follow-ups (B6.1) | Export stays **JSON only** (contract); CSV only if users or regulators ask. The archive is downloaded through the authenticated API (ciphertext only the backend opens), not a bucket URL. The `qal-exports` bucket gets a 7-day lifecycle and backend-only credentials (release checklist). Chunked archives above 64 MiB only if ever needed. "Export ready" notification comes with notifications (D16). Billing tables join the export with M4. One undecryptable row fails the whole export (no silent gaps) and raises an alert. Extract the three copies of SigV4 code into one shared platform helper (follow-up). |
| D43 | Privacy screens (A2.6) | The toolbar's `AI_SETTINGS` link opens the **privacy dashboard** (also for on-device-only and blocked-account states). After a **registered** user requests deletion the device signs out and wipes cached account data (tokens, history flag, last export id, sync state; typing data and the personal dictionary stay); they cancel by signing in again within the 14 days. Guests keep their session, since they cannot sign in again. Turning history off also withdraws `SAVE_AI_HISTORY`, so the switch and the consent never disagree. The `DICTIONARY_SYNC` switch lives only on the consents screen. The client sends `saveToHistory: true` whenever the preference and consent are on, without checking the plan: the server's `AiHistoryRecorder` silently keeps nothing without `HISTORY_SYNC` (verified). The consent-text version stays the constant `"1"` until D23's minimum document versions exist, then moves to configuration. `terms_url` and `privacy_notice_url` are placeholders that need real URLs before release (H3.5 checklist). |
